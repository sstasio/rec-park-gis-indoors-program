Photo & Video Storage

Where large media should live, and why

You've settled SharePoint (documents) and AGOL (GIS data) already. The open question is where photos, 360° video, and point cloud/mesh exports should live — these are too large and too numerous for SharePoint, and too expensive to store natively in AGOL at scale.

Why Not Just SharePoint or AGOL for Media?

SharePoint: has per-file and library sync limits, and OneDrive/SharePoint sync clients slow down badly once a library holds thousands of large photo/video/point-cloud files. It's built for documents, not a media library.
AGOL: hosted content storage is billed by credits and adds up fast at building-portfolio scale (hundreds of 360° panos + point clouds + mesh exports per building). AGOL should hold links to media, not the media itself.

Recommended: Azure Blob Storage

Recommendation: Azure Blob Storage, under the City's existing Microsoft 365 / Azure tenant if SF already has one (likely, given SharePoint/M365 use). This keeps photo/video storage in the same governance and identity boundary as your documents, at a fraction of AGOL's per-GB cost, with no new vendor to get through security review.
ReasonDetail
CostBlob storage is priced per GB/month, typically far cheaper than AGOL credits for the same volume of large files
GovernanceSame tenant as SharePoint/M365 — one identity/security boundary, no new vendor onboarding
IntegrationBlob URLs can be stored directly as attribute fields in your AGOL Facilities/Units layers and referenced from Experience Builder Embed widgets
ScalabilityHandles thousands of large files (360° panos, point clouds, mesh exports) without the sync/performance issues SharePoint has at that scale
Access controlSupports both public read (for published tours) and restricted containers (for raw point cloud data) in the same account

Alternatives Considered

OptionVerdict
AWS S3Functionally similar to Azure Blob, but adds a second cloud vendor/identity boundary outside your existing M365 footprint — only worth it if the City already has an AWS relationship elsewhere.
AGOL hosted contentFine for thumbnails/small previews, not cost-effective as the primary store for full-resolution media at portfolio scale.
Dedicated DAMOverkill for this program's size; adds a new subscription and tool for staff to learn without a clear benefit over blob storage + a simple folder convention.
3DVista / Insta360 native hostingConvenient for quick publishing, but keeps your media on a third-party platform outside city governance — fine for a pilot, not for the long-term system of record.

Suggested Folder / Container Convention

rpd-gis-media/
  {FacilityID}/
    exterior/         (PIX4Dmatic point cloud, mesh, orthomosaic)
    interior/         (Polycam DXF, E57)
    360-tour/         (Insta360 stitched panos/video)
    asset-photos/     (barcode/tag closeups)

Store the resulting blob container URL (or per-asset URL) in a MediaURL-style field on your Facilities/Units layer, exactly the same pattern already used for Tour360_URL in the facility page template.
